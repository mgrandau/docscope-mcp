# Journal - December 11, 2025

## Origin Story

Retroactive journal entry. This project was built before the Human-AI Intent Transfer Principles were defined, alongside copilot-confirm and shortly before ai-session-tracker-mcp.

## The Problem

Documentation quality in legacy codebases is invisible. You can see code coverage, lint results, type errors — but "how well is this documented?" has no tooling. On large legacy projects (C#, VB6, C/C++), functions exist with no docstrings, outdated parameter descriptions, or docs that describe what the code did three refactors ago. Nobody knows which functions are worst because there's no way to scan and rank them.

The specific context: Thermo Fisher legacy code — a mix of C#, VB.NET, VB6, and C/C++ that spans decades. Manual doc review doesn't scale. What's needed is automated triage: scan the codebase, score every function's documentation quality, and surface the highest-priority gaps.

## Key Design Decisions

### MCP server, not a standalone tool

The analysis engine is exposed as an MCP (Model Context Protocol) server so VS Code Copilot and Claude Desktop can call it natively. This means the AI assistant can analyze code documentation quality as part of a conversation, not as a separate workflow.

**Rejected alternative:** standalone CLI tool only. Rejected because the primary use case is an AI assistant saying "let me check the doc quality of this file" during a conversation. A CLI tool requires context-switching. MCP keeps the analysis in the flow of work.

**Why both CLI and MCP:** The CLI was added later (#6) for CI/CD pipelines and terminal workflows. The MCP server is for interactive use; the CLI is for automation. Same analysis engine, different interfaces.

### AST for Python, regex for everything else

Python gets AST-based parsing (accurate function extraction, docstring detection via `ast.get_docstring()`). C#, VB.NET, VB6, and C/C++ use regex-based parsing.

**Rejected alternative:** AST parsing for all languages. Rejected because it would require external parser libraries for each language (tree-sitter, Roslyn, etc.), adding heavy dependencies. The zero-runtime-dependency constraint matters — this is an MCP server that gets spawned by VS Code, and startup time and install simplicity are critical.

**Rejected alternative:** regex only (including Python). Rejected because Python's AST module is in the stdlib and gives dramatically better accuracy than regex for docstring detection. When an AST is free, use it.

**The tradeoff:** Regex parsers have known false positive issues (see open issues #11–#16). Comments that look like function signatures, MFC macros that look like functions, preprocessor directives that match function patterns. This is the acknowledged cost of zero-dependency regex parsing.

### Protocol over ABC for BaseAnalyzer

All analyzers conform to the `BaseAnalyzer` Protocol (structural typing) rather than inheriting from an abstract base class.

**Rejected alternative:** ABC with `@abstractmethod`. Rejected for the same reason as copilot-confirm and copilot-journal — Protocol gives structural typing (duck typing with type checker support), no inheritance coupling, and any class that implements the right methods is automatically compatible without declaring it.

### Mixin-based DRY refactor

Quality assessment and priority calculation logic was extracted into `QualityAssessmentMixin` and `PriorityCalculationMixin`, eliminating ~800 lines of duplication across 5 analyzers.

**Rejected alternative:** keep duplicate logic in each analyzer. Rejected because 5 copies of the same scoring algorithm means 5 places to update when thresholds change. The mixin approach keeps language-specific parsing in each analyzer while sharing scoring logic.

**Rejected alternative:** move scoring into the models layer. Rejected because scoring depends on analyzer-specific context (e.g., which quality indicators a language supports). Models should be data containers, not behavior owners.

### Extension-based language routing

Language detection happens by file extension in `routing.py`. A map of extensions → analyzers determines which analyzer handles which file.

**Rejected alternative:** content-based detection (look at the code to guess the language). Rejected because it's unreliable for similar languages (C# vs Java, VB.NET vs VB6) and adds complexity for marginal benefit. File extensions are deterministic.

**Rejected alternative:** require the user to specify the language. Rejected because the MCP use case is "analyze this file" — the user shouldn't have to tell the tool what language a `.cs` file is. The CLI does support `--language` for inline code where there's no file extension.

### Security limits

Code size (5MB), AST depth (100), parse timeout (5s), path length (4096), null byte rejection. `PathSecurityValidator` blocks traversal and symlink escapes.

**Why these limits:** The MCP server is spawned by VS Code and runs with user permissions. A malicious or malformed file could cause the server to hang (regex catastrophic backtracking, deep AST), consume memory (huge files), or escape the workspace (path traversal). These limits bound the blast radius.

**Rejected alternative:** no limits (trust the filesystem). Rejected because MCP servers accept arbitrary file paths from the client. Even in a trusted VS Code environment, a user could accidentally point the tool at a generated file (e.g., minified JS, auto-generated bindings) that triggers pathological regex behavior.

## What This Project Taught Us

1. **Regex parsing has a ceiling.** The open issues (#11–#16) are all regex false positives. Comments that look like code, macros that look like functions, preprocessor directives. There's no clean regex fix for "is this actually code or a comment?" — that's what ASTs solve.
2. **MCP + CLI is the right interface split.** Interactive analysis in conversations, automated analysis in pipelines. One engine, two interfaces.
3. **Mixin-based DRY works for scoring, not parsing.** Parsing is language-specific and should stay in individual analyzers. Scoring is universal and should be shared.
4. **Security limits matter for MCP servers.** They're spawned processes that accept arbitrary input. Treat them like web servers, not scripts.
